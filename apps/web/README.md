# The client

Everything a player sees. This is the **only** part of the project written in TypeScript,
and the only part you can change without touching the simulation.

```bash
pnpm --dir apps/web run dev      # http://localhost:5173
pnpm --dir apps/web test         # unit tests
pnpm --dir apps/web run typecheck
```

The wasm module is rebuilt by `run dev` and `run build`. If you change anything under
`crates/`, rerun `pnpm --dir apps/web run wasm`.

## The line this side must not cross

The client renders a game and reports which buttons are held. It does not decide anything
about the game itself. Concretely, none of the following live here, and none of them
should: piece shapes, rotation and kicks, gravity, DAS and ARR, lock delay, line clears,
scoring, garbage, or what a tick is worth.

That is not tidiness. The same simulation runs on a server at M3, and any rule this side
re-implements is a rule two peers can disagree about. Every value that could tempt you is
already served by the wasm module for exactly this reason:

| Wanted | Ask for it | Do not |
|---|---|---|
| The cells of the falling piece | the frame block | derive from a shape table |
| The shape of a held or queued piece | `pieceShapes()` | write shapes in TypeScript |
| The button an action maps to | `buttonBits(action)` | hard-code the bits |
| Whether a setting is in range | `normalizeSettings()` | clamp it here |
| The frame equivalent of a duration | `centiframes(ms)` | multiply by 0.06 |
| Where a field sits in the frame block | `frameLayout()` | hard-code offsets |

The one piece of timing the client owns is how many whole ticks are owed at a moment in
time, in [`clock.ts`](src/clock.ts).

## Layout

| Path | What it is |
|---|---|
| [`src/main.ts`](src/main.ts) | Wiring: screens, the loop, and what happens when a run ends |
| [`src/clock.ts`](src/clock.ts) | Real time to whole ticks. Nothing else may decide when to tick |
| [`src/input.ts`](src/input.ts) | Keyboard to buttons, including sub-frame presses |
| [`src/modes.ts`](src/modes.ts) | Modes from `modes.generated.json`, and knowing when a run is finished |
| [`src/audio.ts`](src/audio.ts) | Synthesized cues, driven by the tick's event bits |
| [`src/render/board.ts`](src/render/board.ts) | The playfield |
| [`src/render/hud.ts`](src/render/hud.ts) | Hold, next, and the run's numbers |
| [`src/render/palette.ts`](src/render/palette.ts) | Skins |
| [`src/render/piece.ts`](src/render/piece.ts) | Drawing a piece outside the board |
| [`src/settings/`](src/settings) | The generated settings screen and where settings live |
| [`src/replays/store.ts`](src/replays/store.ts) | Recordings and personal bests, in IndexedDB |
| [`src/sim/`](src/sim) | The wasm boundary: loading it, and reading the frame block |
| `src/wasm/` | Generated by `wasm-pack`. Not checked in, never edited |

## Tuning

Things you are meant to change, and where:

**Look.** [`palette.ts`](src/render/palette.ts) is a list of skins; adding one is an entry
plus a matching variant in `Cosmetic::FIELDS` in the engine, so the option appears in
settings. [`style.css`](src/style.css) is the whole visual design. `CELL` in
[`main.ts`](src/main.ts) is the board's pixel scale.

**Feel that is not simulation.** `BUFFER_ROWS` in [`board.ts`](src/render/board.ts) sets
how much spawn buffer stays on screen. Cue pitch, length and loudness are the numbers at
the top of [`audio.ts`](src/audio.ts). `MAX_CATCHUP_TICKS` and `STALL_MS` in
[`clock.ts`](src/clock.ts) decide how a hitch is handled.

**Feel that is simulation.** DAS, ARR, soft drop, lock delay and the rest are engine
settings. Change them in the settings screen, not in code. If a *bound* is wrong, that is
`crates/engine/src/config/`, and the control follows automatically.

**Screens.** [`index.html`](index.html) holds the markup; `main.ts` wires it. There is no
UI framework — `SPEC.md` §4 says none until it hurts.

## Adding a setting

You do not edit this side. Add the field and its descriptor in
`crates/engine/src/config/`, run `cargo run -p config --bin emit-schema > config-schema.json`,
and the control appears with its bounds, step, unit and help text. CI fails if the schema
falls behind the engine.

## Tests

`vitest`, beside the code they cover. They deliberately do not test the DOM: what is worth
pinning is the logic under it — that the tick count tracks elapsed time under a ragged
clock, that a sub-frame tap is not lost, that a goal ends on the right tick, that a topout
sets no personal best.

Two things this side cannot check, both in CI as scripts:
[`client-parity.sh`](../../scripts/client-parity.sh) proves the built module reproduces
recorded games, and [`capture-roundtrip.sh`](../../scripts/capture-roundtrip.sh) proves a
game captured here is one the tools accept.

`window.openstacker` exists in dev builds only, and is how the client is driven without a
display.
